Executive summary
  • The optimizer found a configuration +45.5% goodput over baseline (3131 vs. 2152 tokens/s) that still satisfies both the 1500ms TTFT P95 and 300ms ITL P95 SLA.
  • 5 independent top trials all converge on attention_backend=FLASHINFER + kv_cache_dtype=fp8 — reconfirming 0-explorative's own finding under a completely different (real ShareGPT / goodput-constrained) methodology.
  • max_num_seqs is the strongest continuous driver of throughput found here (top trials average ~754 vs. ~336 for the worst); gpu_memory_utilization shows almost no effect within its tuned [0.85,0.95] range.
  • scheduling_policy and async_scheduling show essentially no measurable effect on the goal metric in this data.
  • 1 of 30 optimize experiments produced no usable score (not a workflow crash — experimentsWithErrors: 0); not investigated further.

Results overview

Akamas' stability windowing searches each trial's full 150→1024 concurrency sweep for the best throughput sub-window where both SLA constraints hold, and scores that window — not a whole-trial average including the later, saturating portion. Every one of the 30 scored experiments (baseline included) found such a window.

Continuous parameters

max_num_seqs is the standout continuous driver: the top-5 trials average 754, the bottom-5 average 336 — more than double. gpu_memory_utilization shows almost no separation (top-5 avg 0.908 vs. bottom-5 avg 0.907, essentially identical) despite spanning the full tuned [0.85, 0.95] range — consistent with ROADMAP.md H2's own "weak correlation" finding on a different study, now echoed here.

Caveats & data-quality notes

Export-bundle analysis pitfall (found producing this report): the akamas-study-analyzer plugin's bundled script assumes last-optimization.json array index i = experiment i+1. For this bundle that mapping is wrong — the true mapping is i+2 (the baseline experiment is excluded from the arrays entirely). Using the script's assumption produced a completely fabricated first draft of this report (every trial appearing to violate the SLA). Caught by cross-checking every score against logs.json's own "Computed score for trial N.1 is VALID/INVALID: <value>" messages — all 29 scored optimize trials matched exactly at +2, zero matched at +1. Flagged in the plugin's own reference/export-schema.md.
metricConstraintsViolations[i] in the same file does not describe whether experiment i's scored value violates the goal's constraints — with stability windowing active, the scored window is specifically selected from the constraint-satisfying windows within the trial; the violations array reflects a different, worse window in the same trial. Every one of the 30 scored experiments in this bundle shows VALID in logs.json despite most showing nonzero entries in that array.

Exact TTFT/ITL P95 values for the winning window aren't restated numerically here — logs.json confirms compliance qualitatively; the precise per-trial figures would require correlating the selected window's timestamps against the raw metrics-vLLM-time_to_first_token_p95.json/ metrics-vLLM-inter_token_latency_p95.json timeseries in export.gz (not done here).

Recommendations

  1. Carry attention_backend=FLASHINFER + kv_cache_dtype=fp8 + max_num_seqs≈750-800 forward as a strong starting point for future studies on similar hardware/model size — confirmed by 5 independent trials here, and it reconfirms 0-explorative's own finding under a different methodology.
  2. Consider dropping or narrowing gpu_memory_utilization's tuned range in a future study of this shape — it showed almost no effect within [0.85,0.95], so search budget spent there could go to a parameter that actually moves the goal.
  3. scheduling_policy and async_scheduling likewise showed no measurable effect here — worth re-checking with a larger sample before continuing to tune them by default in similar future studies.
  4. For any future analysis of an Akamas export bundle: verify the array-to-experiment offset against logs.json before trusting last-optimization.json array positions, and treat metricConstraintsViolations[i] as informational only, never as a pass/fail signal for the scored value — see "Caveats" above.
